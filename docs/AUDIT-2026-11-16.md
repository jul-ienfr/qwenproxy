## 0. Méthode, périmètre et limites

Trois audits parallèles (architecture, performance, fiabilité/sécurité/tests) ont été menés en lecture seule, puis **les constats Critique et Élevé ont été re-vérifiés par lecture directe** avant publication. Aucune modification de code source n'a été effectuée pendant l'audit. Aucun test live n'a été lancé.

### Niveaux de preuve utilisés dans tout le document

| Marque | Signification |
| --- | --- |
| ✅ | Vérifié par lecture directe du fichier cité, ou par commande exécutée |
| ◐ | Vérifié par lecture directe d'un auditeur ; non re-vérifié ensuite |
| ○ | Non vérifié / hypothèse structurelle — à instruire avant décision |

### Limites assumées

- Les trois auditeurs ont eu l'outil `bash` **refusé** par les règles de permission globales. Leurs inventaires automatisés (graphe d'imports, orphelins de tests, `process.env`) ont donc été **refaits directement** et figurent ici comme ✅.
- La ligne `test:mock` de `package.json:40` est tronquée à 2000 caractères par les outils de lecture ; l'inventaire a été obtenu en parsant le JSON complet, pas la ligne affichée.
- **Aucun benchmark n'a été exécuté.** Les constats de complexité algorithmique sont établis par lecture du code, pas par mesure. Le plan 016 exige une mesure avant chaque correctif de performance.
- Modules jamais lus : `Dockerfile`, `routes/upload.ts` (credentials OSS), `gui/*`, `api/docs.ts` (XSS `innerHTML`), `services/qwen.ts` au-delà des lignes citées, corps des 166 fichiers de test. Les constats les concernant sont marqués ○.

### Convention de comptage des lignes

`LOC` désigne les **lignes non vides** (`Measure-Object -Line`). Le nombre de lignes physiques est supérieur : `src/api/server.ts` = 1 342 LOC / 1 463 lignes physiques ; `src/core/database.ts` = 601 LOC / 670 lignes physiques. Les numéros de ligne cités dans ce rapport réfèrent aux **lignes physiques** (celles affichées par un éditeur).

## 3. Sécurité

### S1 — 🔴 CRITIQUE — DNS rebinding → prise de contrôle admin complète ✅

**Installation concernée** : configuration **par défaut** (bind loopback, aucune `API_KEY`).

**Chaîne de causes, vérifiée ligne par ligne** :

1. `src/core/config.ts:26` — bind par défaut `127.0.0.1`.
2. `src/core/auth-identity.ts:115-118` — si `!apiKeyConfigured`, `resolveIdentity([])` retourne `LOCAL_ADMIN_IDENTITY` (rôle **admin**) **sans aucune vérification d'adresse socket ni de Host**.
3. `src/admin/auth.ts:190-198` — le chemin legacy « no-key » accorde l'admin après le seul contrôle `rejectCrossOriginMutation`.
4. `src/admin/auth.ts:136-161` — ce contrôle compare `new URL(origin).host` à `new URL(c.req.url).host`. En rebinding **same-origin**, l'attaquant sert sa page sur `evil.com:7936` puis fait pointer le DNS vers `127.0.0.1:7936` : `Origin = evil.com:7936`, `Host = evil.com:7936` → **égalité** → mutation autorisée. Le navigateur considère la requête same-origin : **ni preflight, ni restriction CORS**, y compris PUT/DELETE. Si `Origin` est absent, `:139` retourne `null` (autorisé) — le résultat est identique.
5. **Aucune validation du `Host` entrant n'existe dans tout `src/`** ✅ — vérifié par grep exhaustif (`isTrustedHost`, `hostAllowed`, `assertHost`, `remoteAddress`). Le seul `remoteAddress` est `src/admin/app.ts:84-88`, utilisé pour le throttling de login, pas pour l'autorisation.

**Faux ami écarté** ✅ : `src/core/internal-origin.ts` (37 lignes) ne fait que **dériver l'origine des auto-appels sortants** entre adaptateurs (`getInternalOrigin`). Ce n'est pas une validation entrante. Il ne couvre donc pas S1.

**Impact** : un site web malveillant obtient l'admin complet — modification de `PROXY_URL` (MITM de tout le trafic Qwen), ajout de comptes, création d'utilisateurs admin, lecture des logs et de la liste des comptes. Le cookie `SameSite=Strict` (`admin-session.ts:176`) est sans effet : le chemin legacy **n'exige aucun cookie**. Les GET deviennent lisibles (same-origin), donc exfiltration en plus de l'écriture.

**Correctif** : allowlist du `Host` entrant (loopback + host bindé + domaines de confiance explicites, port inclus), vérification `socket.remoteAddress` loopback pour le chemin no-key, et exigence d'une clé pour toute mutation admin. Ne jamais se reposer sur la seule comparaison Origin/Host.

**Non couvert par les tests** ✅ : `admin-dashboard.test.ts` contient « legacy no-key mutations still reject a cross-origin browser » (passe) et « origin checks tolerate a TLS proxy but reject another host » (passe). Aucun ne teste le cas **Origin == Host == domaine attaquant**.

### S2 — 🟠 ÉLEVÉ — Cookies et refresh_tokens Qwen en clair, répertoire DB world-readable ✅

- `src/core/database.ts:504-556` (`saveAuthSession`) : `session.cookie` est écrit **directement** en `:540`, `session.refreshToken` en `:552`. **Aucun appel à `encrypt()`.** Vérifié sur les 53 lignes de la fonction.
- `src/core/database.ts:45` : `fs.mkdirSync(DB_DIR, { recursive: true, mode: 0o755 })` — répertoire **world-readable**. Le fichier DB créé par better-sqlite3 hérite des permissions par défaut (0644 typique).
- Contraste ✅ : `.encryption_key` en 0600 (`crypto-utils.ts:34`), `.admin_session_secret` en 0600 (`admin-session.ts:56`), `model-mappings.json` en 0600 (`model-mapping.ts:521`). Seuls `accounts.password` et `accounts.proxy` sont chiffrés.

**Impact** : sur Linux multi-utilisateurs ou Docker avec volume partagé, tout utilisateur local peut lire `data/db/qwenproxy.db` et voler les cookies/refresh_tokens → accès aux comptes Qwen. **Violation directe du principe III de la constitution** (« Credentials MUST be encrypted at rest »). Sur Windows les modes POSIX sont ignorés (ACL) : risque moindre, mais posture incohérente.

**Correctif** : chiffrer `cookie`, `bx_ua`, `bx_umidtoken`, `refresh_token` au repos avec le mécanisme AES-256-GCM existant + migration des lignes en clair ; `DB_DIR` en 0700, fichier DB en 0600 ; aligner `paths.ts:ensureDataDirs`.

### S3 — 🟡 MOYEN — Déchiffrement silencieux → credentials perdus sans diagnostic ◐

`src/core/accounts.ts:246-250` : `decrypt(row.password)` en `catch` → `password = ""`. ## 4. Fiabilité

### R1 — 🟠 ÉLEVÉ — Exceptions process avalées sans sortie ✅

`src/core/process-guard.ts:57-83` (fichier de 84 lignes, lu intégralement) : pour toute erreur **non bénigne**, le handler fait `console.error(...)` puis **retourne implicitement**. Le processus continue dans un état indéfini. Installé globalement par `src/index.ts:33`, `login.ts:15`, `clean-cache.ts:9`, `delete-chats.ts:5`.

Aggravation — la définition de « bénin » est très large (`:10-27`) : `"Protocol error"`, `"Connection closed"`, `"Assertion error"`, `"Target closed"`, `"Page crashed"`… Plus `:30` `if (!error) return true` et `:31-37` un objet vide `{}` traité comme bénin. Un vrai bug peut donc être classé bénin **et** silencieux.

**Correctif** : teardown bénin → continuer ; toute autre erreur → log puis `process.exit(1)` sous supervision. Resserrer les motifs bénins (exiger un marqueur Playwright/CDP, pas une substring générique).

### R2 — 🟠 ÉLEVÉ — Arrêt « gracieux » : navigateur fermé AVANT le drain ✅

`src/api/server.ts:1039-1115` (`cleanupServerResources`), ordre réel vérifié :

```text
watchdog.stop → metrics.stop → cache.close → stopSessionKeeper → deleteChats
  → closeAllPlaywright()      (:1073-1074)   ← navigateur fermé ICI
  → server.close() drain      (:1076-1094)   ← requêtes en cours drainées APRÈS
  → flushLogicalThreadState   (:1096-1102)
  → shutdownRedisPersistence  (:1104-1111)
  → closeDatabase             (:1113-1114)
```

Le commentaire `:1079-1081` affirme « Drain in-flight requests BEFORE flushing » — vrai pour le flush DB, **faux pour le navigateur**. Les streams SSE en cours dépendent de la page Playwright : ils échouent en milieu de génération. L'arrêt « gracieux » casse les requêtes actives.

**Correctif** : drainer `server.close()` d'abord, puis fermer Playwright/Redis/SQLite.

### R3 — 🟠 ÉLEVÉ — Perte définitive du hold de quota sur erreur DB transitoire ✅

`src/core/account-model-limits.ts:42-46`, vérifié :

```ts
function ensureLoaded(): void {
  if (loadedFromDb) return;
  loadedFromDb = true;   // :44  ← flag posé AVANT le chargement
  loadModelLimits();     // :45
}
```

Or `loadModelLimits` (`:158-174`) avale toute erreur DB dans `catch {}` (`:171-173`). Si la première lecture échoue (DB verrouillée, `busy_timeout` dépassé), `modelLimits` reste vide **pour toute la vie du processus** — le flag n'est jamais réinitialisé.

Persistance elle-même best-effort silencieuse : `:69`, `:90`, `:118`, `:130`, `:140` (5 `catch` muets). À noter : `:136` (`clearAllModelLimits`) pose le flag à `true` **volontairement** — après un vidage, il n'y a rien à charger. Ce n'est pas le même défaut.

**Impact** : un compte ayant épuisé son quota quotidien sur un modèle n'est plus mis en quarantaine → rotation vers ce compte → échecs répétés. Contourne le hold incrémental introduit par `2f84660`.

**Correctif** : ne poser le flag qu'après chargement réussi ; retry borné ; logger les échecs de persistance.

### R4 — 🟠 ÉLEVÉ — Hook de test actif en production ✅ (partiel)

`src/core/config.ts:123-124` ◐ : les défauts `RETRY_BASE_DELAY_MS`/`RETRY_MAX_DELAY_MS` passent à 50/200 si `TEST_MOCK_QWEN_AUTH === "true"`, **sans garde `NODE_ENV`**. Le mock auth lui-même **est** gardé (`auth-playwright.ts:21-26`, `playwright.ts:2244/2404/2547`). `TEST_MOCK_QWEN_AUTH` n'est pas documenté dans `.env.example`.

**Impact** : même mock auth désactivé, une variable de test qui traîne en prod réduit les délais de retry à 50/200 ms → tempête de retry.

### R5 — 🟡 MOYEN — La récupération des streams du watchdog est un no-op ◐

`src/core/watchdog.ts:167-169` : `recoverStreams()` émet seulement `"recovery:streams:throttled"` et **ne fait rien**. La détection existe (`:96-103`), la métrique existe (`stream-registry.ts:38,80`), le seuil existe (`WS_CRITICAL` = 100). Aucune action. La congestion n'est jamais résolue, mais le statut rapporte une récupération.

### R6 — 🟡 MOYEN — Pas de sortie forcée, handlers de signaux installés tard ✅

`src/api/server.ts:1117-1123` : `handleSignal` await `stopServer()` puis `exit(0)` — **aucun timer de forçage**. Si `server.close()` ou `closeAllPlaywright()` pend, le processus ne sort jamais. `installSignalHandlers` est appelé en `:1401-1403` ◐ **après** le warmup des comptes : pendant le warmup, SIGINT/SIGTERM = terminaison immédiate sans nettoyage (navigateurs orphelins, DB non flushée).

### R7 — 🟡 MOYEN — Pas de disjoncteur global ◐

## 5. Performance

> ⚠️ Aucun benchmark n'a été exécuté. Les complexités ci-dessous sont **démontrées par lecture**, pas mesurées. Le plan 016 impose un bench micro en échec avant chaque correctif.

### P1 — 🔴 CRITIQUE — Copie quadratique de la réponse en mode incrémental ✅

**Mécanisme exact, vérifié sur `src/routes/chat/helpers.ts` (323 lignes)** :

```ts
// :10-17
function buildDeltaResult(delta: string, matchedContent: string): DeltaResult {
  return { delta, matchedContent,
    contentLength: matchedContent.length,
    contentSuffix: matchedContent.slice(-32) };   // :15
}
// :82  — branche « strictly incremental »
return buildDeltaResult(newStr, oldStr + newStr);
```

`oldStr + newStr` produit une **cons-string** V8 (O(1), non aplatie). Puis `:15` appelle `.slice(-32)` dessus, ce qui **force l'aplatissement de la totalité de l'accumulé** → copie O(n) **à chaque chunk** → **O(n²)** sur le flux.

**Nuance importante que l'audit initial n'avait pas isolée** : le fast-path cumulatif (`:35-46`) retourne `buildDeltaResult(newStr.slice(previousLength), newStr)` où `newStr` est **déjà plat** — le `slice(-32)` y est O(32). Le défaut quadratique est donc **spécifique à la branche `:82`** (delta strictement incrémental, sans préfixe commun). Le commentaire `:32-34` est lui-même contradictoire (« Fast path for cumulative Qwen chunks … since Qwen streams with incremental_output=true »), ce qui explique la confusion.

**Impact estimé** : réponse 1 Mo en deltas de 1 Ko → ~1 000 chunks × ~500 Ko moyens ≈ **500 Mo copiés par stream**, plusieurs centaines de ms à plusieurs s de CPU bloquant l'event loop.

**Correctif (faible risque, O(32) garanti)** : calculer le suffixe sans jamais aplatir l'accumulé —

```ts
const suffix = newStr.length >= 32
  ? newStr.slice(-32)
  : (oldStr.slice(-(32 - newStr.length)) + newStr);
```

### P2 — 🔴 CRITIQUE — Re-scan de la ligne SSE entière à chaque chunk ✅

`src/routes/chat/streaming.ts:2011-2013` : la regex fast-path est **ancrée `^…$`** et capture le champ `content` sur toute la ligne :

```text
/^\{"response_id":"[^"]*","choices":\[\{"delta":\{"content":"((?:[^"\\]|\\.)*)"\}\}\]\}$/
```

En mode cumulatif chaque ligne SSE contient la réponse entière déjà émise → O(n) par chunk → **O(n²)**. Le fallback `JSON.parse(dataStr)` (`:2060` ◐) a le même coût.

**Correctif** : extraction incrémentale du champ `content` sans re-scanner le préfixe, ou négociation de deltas non cumulatifs upstream.

### P3 — 🔴 CRITIQUE — Décodeur d'échappements : 4 passes **et 3 défauts de correction** ✅

`src/routes/chat/streaming.ts:2015-2019`, vérifié :

```ts
const unescaped = fastMatch[1]
  .replace(/\\n/g, "\n")
  .replace(/\\t/g, "\t")
  .replace(/\\"/g, '"')
  .replace(/\\\\/g, "\\");
```

1. **Bug d'ordre** : `\n` est traité **avant** `\\`. Un littéral backslash+n (chemin Windows `C:\new`, ou `\n` dans du code) est corrompu en backslash+newline.
2. **`\uXXXX` n'est pas décodé** — un `\u00e9` upstream est livré tel quel au client au lieu de `é`. *(Constat ajouté par la re-vérification ; absent de l'audit initial.)*
3. **`\r`, `\/`, `\b`, `\f` ne sont pas décodés** non plus.

**Correctif unique, à la fois plus rapide et correct** : une seule passe native —

```ts
const unescaped = JSON.parse('"' + fastMatch[1] + '"');
```

La regex garantit déjà que la capture est un corps de chaîne JSON échappé ; `JSON.parse` gère tous les échappements légaux dans l'ordre correct. **4 allocations → 1**, et les 3 défauts disparaissent.

### P4 — 🔴 CRITIQUE — Parseur tool-call O(n²) sur les gros payloads ◐

`src/tools/parser.ts:2132` `this.buffer += chunk` ; `:2232` à **chaque `feed()`** tant que `insideTool`, appel `findToolEndOutsideJsonString(this.buffer)` sur le buffer accumulé **entier**. ## 11. Synthèse en une page

**Le projet n'est pas mal construit — il est mal borné et mal vérifié.**

Les mécanismes difficiles sont **corrects** : concurrence à epoch, leases avec sweep, single-flight, DNS pinning, redaction, hash des clés, chiffrement des mots de passe, cooldowns bornés, nettoyage de stream complet, 0 `@ts-ignore`, typecheck vert, 0 vulnérabilité, 166 fichiers de test.

Quatre familles de défauts dominent :

1. **Une faille de sécurité critique par défaut** (S1) : aucune validation du `Host` entrant + fallback admin sans clé + comparaison Origin/Host contournable en same-origin. Une page web hostile prend l'admin complet sur une installation par défaut.
2. **Des coûts quadratiques dans le hot path** (P1 P2 P4) et une absence de backpressure (P5) : le prix se paie sur les longs tours d'agent, exactement l'usage cible. P3 est en plus un **bug de correction** (`\uXXXX` non décodé, ordre des échappements).
3. **Des transitions d'état non fiables** (R1 R2 R3 R6) : crash avalé sans sortie, navigateur fermé avant le drain, hold de quota définitivement perdu sur erreur transitoire, arrêt sans borne de temps.
4. **Un gate de vérification cassé** (T1 T2 T3 T4) : la suite par défaut est rouge pour une raison non attribuable, 43 assertions vertes dont toute la sécurité multi-utilisateurs ne sont jamais exécutées, et `npm test` touche le réseau.

**La vague 1 est le levier** : réparer le gate (4 tâches, effort faible) rend tout le reste mesurable et attribuable, puis ferme la faille critique. Les vagues 2 à 4 se livrent ensuite par incréments indépendants, sans big-bang.
